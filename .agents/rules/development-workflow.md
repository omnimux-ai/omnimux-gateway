# Agent 决策与跨会话交接

先查本任务已确认的目标、范围和验收条件。新需求按[研究流程](../../AGENTS.md#research-before-design-fork)提出方案。接手已有任务从下文的交接记录恢复进度。公开案例可辅助设计，实际授权以用户原话为准。

## 谁决定下一步

| 判断依据 | Agent 的下一步 |
| --- | --- |
| 范围清楚，动作已获授权或属于常规开发，可撤销，验收结果可观察 | 自主选择与现有实现相容、改动最小的方案，执行适用检查，再从用户入口验收。常规调查、测试、修复和复测可连续完成。 |
| 两个判断会产生不同结果，现有证据不足 | 先做最小的可逆实验，记录什么结果能区分它们。仍需决定用户体验、业务取舍或扩大成本、权限、风险时，一次列清待定事项和影响，继续独立可做的工作。 |
| 下一步触发仓内人工门禁 | 核对同一任务已批准的对象、行为和范围。前端演示、受保护行为、合并与生产操作遵循[网关规则](../../AGENTS.md#fork-specific-rules-omnimux)。在确认方案时一并记录是否授权合并。有多个决定时可在同一轮说明各自对象与影响，有明确批准的部分直接继续。 |

例如，下载文案的 HTML 演示已确认，Agent 可以改已确认的文案并验收下载菜单。若同时发现钱包页面需要调整，先完成下载任务，另外说明钱包行为及所需授权。同一工单的开发批准不能作为上线凭据。

## 如何判定验收通过

1. 动手前把需求写成可观察的结果。写明入口、输入、预期输出和目标环境。修复问题时尽量让同一用例在旧版复现、在修复版通过。旧环境无法复现时记录限制和替代证据。
2. 按[仓内验证矩阵](../../AGENTS.md#commands--verify)选覆盖改动的检查。先运行最小且能区分对错的用例，再覆盖受影响的入口、失败路径或兼容范围。自动化能实际走完目标入口时，Agent 自行验收。例如按钮文案变更可以从页面打开菜单，核对各语言的按钮名称及下载目标。
3. 对每条验收条件记录版本、环境、实际结果和证据。测试通过、被跳过、无法验证分别记录。模拟上游只能证明相应模拟场景；发布、合并队列、线上行为各取对应目标的独立结果。对未提交改动注明工作树差异，不能只用当前提交号代表文件内容。
4. 失败时先判断是实现、测试、环境还是证据过期。可恢复的问题自行修复，复测受影响范围。外部操作结果不明时先回读，避免重复操作。关键条件仍无证据，只报告已验证的部分和剩余阻塞。

## Agent 审查与提交 PR

1. 负责实现的 Agent 在开 PR 前准备提交、正文和验证证据，在正文记录[文档影响](#文档影响)，委派未参与本次实现和正文起草的 Agent 独立审查。审查 Agent 核对相对目标分支的差异、需求范围、回归风险、文档影响、实际验证结果和公开仓边界，给出审查结论。
2. 有阻断问题时，由实现 Agent 修复并送独立 Agent 复审。提交变化时复审新版本，正文事实变化时复核相关内容。审查通过后，将已审提交 SHA、审查结论、核对过的验证证据和未验证项写入 PR 正文，由实现 Agent 提交。
3. 核对远端 PR 的最新提交与已审版本一致，并按[合并与验收流程](../../AGENTS.md#wait-and-resume-fork)跟进必需检查。审查通过、必需检查通过且已有合并授权时，Agent 自行入队。合并后按实际合入版本验收，汇报用户能看到的效果、验证结果和未验证项。

### 文档影响

- **实现者**根据目标分支与待提交版本的差异，找出已记录的接口、默认值、运行路径、状态、兼容性、错误行为或长期规则的变化。按[文档同步规则](../../AGENTS.md#docs-sync-fork)更新对应的仓内说明，并在 PR 正文列出变更、文档链接及相关实现或验证依据。无影响时，写明依据。
- **跨仓文档**在开 PR 前记录受影响页面、关联文档 PR 或任务、当前状态及发布验收条件。公开 HTTP API 或模型目录变更在获得授权并完成目标环境的 smoke 后，核对已发布的中英文文档与更新日志，再将文档同步记为完成。正文只链接可公开的材料。
- **独立审查者**对照目标分支与待提交版本的实现和验证证据，核对文档内容、源文件链接及无影响的依据。应随 PR 更新的内容有遗漏，或跨仓跟进缺少可追踪记录时，先补齐再通过审查。

## 换会话后如何继续

- **定位任务。** 以同一 Issue、PR 或任务标识定位独立工作树。一次只由一位负责人更新任务记录或提交该工作树，并行工作划分文件归属。接手前核对是否仍有写入者或等待任务，避免重复实现和重复排队。
- **维护一份交接记录。** 优先复用已授权的持久任务记录。保存目标和逐项验收条件、负责人、分支与版本、授权原话出处及适用边界、研究或方案链接、已验和未验结果、下一步和阻塞。遇到交接、等待或重要状态变化时更新。公开 Issue 或 PR 只承载适合公开且已获准发布的内容，内部记录和原始证据按仓库边界保存。
- **找到原记录。** 本机独立工作树可在 Git 返回的 `git rev-parse --git-path agent-handoff` 位置保存一行任务记录地址，只作为索引读取。跨机器或工作树移除后，使用任务标识和已授权共享的记录地址；在移除工作树前确认待接手者能访问它。仅保存在本机的记录适用于本机接手。
- **重新核实。** 读取根规则和受影响目录规则，核对当前差异、提交、授权来源、PR 版本和最新检查。在相同验收条件、输入、版本和环境下复用已有结果。版本、环境或目标变化时重验受影响部分，重新判断授权是否仍覆盖。找不到交接记录时，先从可验证的工作树、Issue、PR 和检查重建；无法核实的授权保留为待确认。
- **改进重复工作。** 如果同类漏检再次发生，优先把稳定、可判断的条件加进已有测试或检查。比较同类任务的重复确认、旧版证据被误用和验收后返工次数，同时记录任务总数；有记录后再判断自动化效果。
