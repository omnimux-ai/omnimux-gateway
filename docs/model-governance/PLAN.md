# 全面模型治理计划

> 起因：一个"参考图上限"的数字被凭空写出并上线，用户追问后才发现——问题不是这一个数字，
> 而是**我们对 100 个模型的对外主张，从来没有事实来源、没有验收、没有门禁**。
> 这份计划把"模型"当作一类需要治理的资产，而不是一堆配置行。

## 一、问题定性：六类治理缺失（都已在线上发生过）

| # | 缺失 | 已经造成的后果 | 根因 |
| --- | --- | --- | --- |
| 1 | **事实无出处** | 参考图上限被写成"1 张"，与实际 16 张不符 | 限制数字存在代码里，没有来源字段，也没有校验 |
| 2 | **主张无验收** | 模型页对所有生图模型无条件标"图生图"，而当时根本没有图生图通路 | 能力标签由标签推导，不由实测背书 |
| 3 | **对接无文档** | 公开接口文档里生图模型页只写提示词/张数/尺寸，**没有参考图字段与限制** | 文档手写，与实现无对照关系 |
| 4 | **结果不可取** | 异步任务的图片地址对外接口取图超时（502/504） | 关键路径缺端到端验收 |
| 5 | **配置靠手工** | 渠道/模型/分组/定价散落多处，靠人记 | 已有 baseline 门禁，但覆盖不到模型事实 |
| 6 | **无生命周期** | 模型进入目录没有任何准入检查，下线也没有流程 | 没有"模型档案"这一实体 |

一句话：**我们治理了代码，治理了配置，但没有治理"我们对模型说了什么"。**

## 二、治理对象：把"模型档案"变成一等公民

已经在做（本计划的地基）：

- **契约**：`docs/model-governance/CONTRACT.md` —— 每个模型一份 JSON 档案，
  限制数字**必须**带官方出处（url + 原文引述 + 核验日期），查不到就写 `unverified` 并列出未知项。
- **落盘**：`docs/model-governance/specs/<model_id>.json`，一模型一文件，可复用（模型规格很少变）。
- **门禁**：`scripts/ops/check-model-specs.mjs` —— 目录里每个模型都必须有档案；
  必填字段齐、`sources` 合规、家族字段齐、`unverified` 必须写明未知项。任一条不满足即失败。

这套东西的价值在于**它把"我调研过了"变成了可核验的产物**。

## 三、六条治理线（每条都要有门禁，不靠自觉）

### 线 1｜事实治理：模型档案

- 交付物：100 份档案（8 个代理分头调研，本计划执行中）。
- 门禁：`check-model-specs.mjs`。
- 判据：档案里每一个数字都能点到官方页面的原文。

### 线 2｜能力治理：说的和做的一致

- 规则：**模型页/表单里的每一项能力主张，必须同时满足两条**——
  (a) 档案里 `operations` 声明了它；(b) 有一条最近的真实调用证据。
- 门禁（待建）：`check-capability-claims.mjs`
  - 扫前端能力标签与表单控件的推导逻辑，凡是"由标签推导"而非"由档案支撑"的主张，列出并失败。
  - 例：所有生图模型无条件标"图生图"这种写法，直接被拦下。
- 目标：消除"页面标了但做不到"。

### 线 3｜文档治理：对外口径与档案对齐

- 规则：公开文档的模型页字段表，必须与档案一致（字段名、限制、错误形态）。
- 门禁（待建）：`check-docs-coverage.mjs`
  - 目录里每个模型 → 是否有中英文页面 → 页面是否覆盖档案声明的 `operations` 与限制。
  - 现状已知缺口：生图模型页缺参考图字段与格式/数量/大小限制（**待授权修改文档仓库**）。
- 产出：文档从档案**生成**而非手写，手写只保留说明性文字。

### 线 4｜路由与绑定治理：渠道、分组、定价

- 已有：`config-baseline` 零漂移、定价账本、FX 单源。
- 补强：把"模型 → 可用分组 → 渠道绑定 → 生效价格"做成一条可核验链，
  任一处改动都必须同步 baseline（已有门禁），并新增"价格锚点必须指向厂商官方价"的检查。

### 线 5｜验收治理：每个能力都有真实调用证据

- 规则：模型 + 操作的组合，必须有**最近一次真实调用**的留档（时间、结果、扣费是否结算）。
- 落盘：`docs/model-governance/acceptance/<model_id>.md`（追加式，不覆盖）。
- 门禁（待建）：`check-acceptance-coverage.mjs` —— 档案声明的 `operations` 都有验收记录，且不过期（季度）。
- 这条直接对应今天发现的第 4 类缺失：图生图通路当时"以为通了"。

### 线 6｜生命周期治理：准入、变更、下线

- **准入**：新模型要进目录，顺序固定为 档案 → 门禁 → 渠道绑定 → 文档 → 真实验收 → 上线。
- **变更**：厂商改规格 → 更新档案 `checked_at` 与 `sources` → 同一变更集里同步前端限制表与文档。
- **下线**：档案标记 `retired`，文档与目录同步，验收记录保留。
- **季度复核**：只更新有变化的档案（成本很低，因为规格稳定）。

## 四、落地节奏

| 阶段 | 内容 | 状态 |
| --- | --- | --- |
| P0 | 契约 + 落盘目录 + 档案门禁 | **已完成** |
| P1 | 100 个模型档案（8 代理分工调研） | 执行中 |
| P2 | 把档案接进前端：限制表由档案驱动，删掉硬编码 | 待 P1 |
| P3 | 能力主张门禁 + 文档覆盖率门禁 | 待 P2 |
| P4 | 验收留档制度 + 季度复核 | 待 P3 |

## 五、与既有门禁的关系

不新造体系，挂在已有机制上：

- 档案变更 → 走 worktree + 核心变更门禁（若触及受保护路径）。
- 档案与 `config-baseline` 同属事实来源 → 同一变更集提交。
- 新增三个检查脚本 → 并入 CI 与本地检查命令，与现有 gate 并列。

## 六、这套东西怎么防"没做对"

用户的原话是：**"他要是没做对吧，你也拿他没办法。"** 应对方式是把"做对"变成机器判据：

1. **不写档案 → 门禁失败**（模型进不了目录）。
2. **写了数字但没有官方出处 → 门禁失败**（`sources` 校验）。
3. **说了能力但没有验收记录 → 门禁失败**（P3/P4 建成后）。
4. **文档与档案不一致 → 门禁失败**（P3 建成后）。
5. **查不到就老老实实写 `unverified` + 未知项** —— 这是**允许**的结果，
   "编一个看起来合理的数字"才是失败。规则上鼓励诚实的不确定，惩罚漂亮的编造。

这五条落地后，AI 也好人也罢，"没做对"会在提交那一刻被拦下，而不是等用户发现。
